# Swells R1 and surface-aware design

Date: 3 September 2026  
Status: implementation started

## Intent

Swells should expose different views of the same sensing model on different physical surfaces. The Rabbit R1 is the first constrained interactive surface because capture, voice, one-at-a-time exploration and Swells' existing visual language are a particularly good fit.

This is not a responsive redesign of the desktop application. It is a surface-specific projection.

## Product boundary

Attention asks: **What needs me?**

Swells asks: **What am I noticing, and what is forming?**

Attention may point at a Swells signal, but it must not duplicate or own the Swells observation/signal model.

## Semantic model and projection

Three layers stay separate:

1. **Canonical state** — observations, signals, reflections, sentiment, evidence and user permissions.
2. **Semantic scene** — a read-only description of what Swells currently knows: temperature, active swells and changes.
3. **Surface projection** — what a particular device can usefully and safely render.

Surface projection is pure: it can rank, truncate and simplify, but must not mutate canonical state.

## Surface profiles

### R1

- 480 × 640
- full colour and animation
- touch, swipe/wheel and voice
- one primary item
- small exploration depth
- durable simple capture allowed
- evidence inspection only by hand-off or concise summaries

### Tablet

- full colour
- several simultaneous swells
- richer exploration and evidence
- voice + touch

### E-paper

- mono/limited colour depending hardware
- no animation
- ambient, room-distance viewing
- one primary statement
- no durable writes

## R1 lenses

### Notice

Fast observation capture. No taxonomy or signal selection before capture. The existing Swells processing pipeline decides what the observation may connect to after it is safely stored.

### Temperature

Uses the existing “temperature of things” semantics.

Warm: more energised / urgent.  
Cool: more calm / reflective / uncertain.  
Neither is better.

The R1 projection favours a single ambient reading, a subtle direction compared with the previous period, and observation count. It must not turn temperature into an importance score.

### Horizon

A bounded set of active signals, ordered for usefulness rather than displayed as a dashboard. One signal is foregrounded at a time.

### Swell

One signal with:

- title;
- concise description;
- strength;
- direction;
- observation count;
- contributor count.

Evidence remains addressable by signal ID even where it is not all shown on-device.

### Change

Foreground a signal already marked new or strengthening. This is a projection of existing Swells state, not a new alert model.

### Ask

A bounded conversation with a selected signal and its exact evidence. Ask is deliberately deferred until the read surface and device interaction are stable.

## Interaction grammar

- **wheel / swipe** — next or previous item;
- **tap** — inspect / choose;
- **Notice** — capture;
- **voice** — capture now; Ask later;
- **back** — return from Swell to Horizon.

R1 should never require conventional multi-level app navigation.

## Lessons carried from Attention Agent

1. Surface contracts belong outside components.
2. Native Rabbit audio is required; WebView microphone behaviour is not reliable enough.
3. TTS must release before microphone capture and resume afterwards.
4. Small-screen copy needs explicit bounds; CSS alone will not rescue desktop-sized content.
5. A pending capture/review must remain visible and resumable.
6. Wheel events should become semantic previous/next navigation, not arbitrary page scrolling.
7. The native shell should authenticate into the device route and return there after sign-in.
8. Device software needs an update path from the start.

## Wider Good Ship direction

The native mechanics are not unique to Attention or Swells. Once the Swells R1 proof is stable, extract the common Android WebView bridge, native recorder, TTS coordination, haptics, immersive mode and updater into a reusable device-shell foundation.

The product-specific layer should then be mostly:

- base URL and auth-return route;
- package/branding;
- surface-specific web experience;
- allowed native capabilities.
